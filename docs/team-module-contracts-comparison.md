# 模块协作规范 V1 与 V2 对比

对比对象：`team-module-contracts.md`（V1）与 `team-module-contracts-v2.md`（V2）
适用前提：学院管理系统将作为商用系统交付。

## 结论

建议采用 V2 作为团队评审稿。V2 没有削弱 V1 的一致性、版本控制和审计要求，而是进一步明确了商用基线，并将数据对象、事务边界、可靠事件和权限结论写得更便于实施。

V1 可以保留作为初稿；团队确认后只维护 V2，避免两份规范同时生效。

## 总体差异

| 维度 | V1 | V2 | 判断 |
| --- | --- | --- | --- |
| 数据归属 | 已明确各模块主数据 | 在此基础上固定 `courseId`、`offeringId`、`enrollmentId` 等核心语义 | V2 更不容易出现错关联 |
| 一致性 | 同时描述共享事务与异步补偿 | 同步强一致与 Outbox 最终一致分别适用不同场景 | V2 的事务边界更明确 |
| 成绩同步 | 使用来源版本，方向正确 | 保留来源版本，并规定单体内事务、幂等键和拆分服务后的迁移要求 | V2 更完整 |
| 请假联动 | 有审批版本、重试和撤销规则 | 固定为事务 Outbox、状态可见、告警和人工处理队列 | V2 更适合商用运行维护 |
| 审计与安全 | 分散在各业务章节 | 增加统一的审计、导出、脱敏、并发和错误码基线 | V2 覆盖更全面 |
| 权限冲突 | 给出建议并保留部分待确认项 | 给出默认实施结论和开放条件 | V2 更便于直接开发 |
| 课程边界 | 主要在权限章节说明 | 单列课程模块负责与不负责的内容 | V2 更适合当前分工 |
| 验收 | 请假场景较详细 | 覆盖班级、成绩、请假和权限 | V2 更均衡 |

## 四个问题的具体对比

### 1 班级数据归属

两版结论一致：年级模块维护年级和行政班主数据；学生模块维护学生当前班级与调班；导员模块维护主辅导员分配；其他模块只引用 `classId`。

V2 增加了两个关键约束：

- 明确行政班与“某学期某门课的开课班级关系”不是同一个实体；
- 历史业务保存发生时的 `classId`，学生调班不能改写历史统计。

因此这一部分 V2 更适合作为正式契约。

### 2 成绩统一存储和计算

两版都采用“双层数据、单一总评”：考务模块保存考试原始分，学习模块维护课程总评、学分和 GPA。

V1 的优势是较早引入 `sourceRevision` 和计算规则版本。V2 完整保留这些要求，并补充：

- 考试原始分唯一键为 `examId + enrollmentId`；
- 课程总评唯一对象是 `enrollmentId`；
- 单体内同步写入使用同一事务；
- `examId + enrollmentId + sourceRevision` 作为同步幂等依据；
- 成绩状态采用草稿、已提交、已发布、已锁定；
- 发布时固化计算规则版本和各分项原值；
- 补考、重修和更正保留历史，不覆盖事实。

V2 对开发、审计和将来系统拆分都有明确路径。

### 3 请假审批和考勤联动

两版都正确地区分了请假审批事实、原始打卡事实和最终考勤状态。

V1 在“同事务调用”和“异步补偿”之间保留选择。V2 根据商用要求固定为事务 Outbox：审批结果和待同步事件一起提交，考勤更新可以可靠重试。这样既不会因临时故障阻塞审批事实落库，也不会在进程中断时丢失联动任务。

V2 还增加同步状态展示、失败告警、人工处理队列、撤销事件和重新计算要求，便于上线后定位问题。

### 4 权限矛盾

两版的推荐结论一致：

- 学委可以为本班发起并编辑调课、补课变更单，不直接修改正式课表；
- 教师可以为本人课程发起并编辑调课、停课、补课变更单，不直接修改正式课表；
- 教师审核本人授课课次的补卡；
- 纪委审核本班同学补卡，不审核本人申请；
- 调停课由管理员或明确授权的教务人员审核。

V2 进一步要求审批使用状态条件和版本号防并发，并明确教师和学委编辑的是“课表变更单”，审批通过后才更新正式课表。辅导员默认不能修改全校课程主数据；若开放课程维护，必须配置院系范围和独立权限。

## V2 相比 V1 新增的商用要求

1. 关键状态使用版本号和乐观锁，防止多人同时操作造成覆盖。
2. 跨模块可靠传播使用 Transactional Outbox，并提供重试、告警和人工处理。
3. 导出设置独立权限，记录审计并对敏感字段脱敏。
4. 批量导入明确事务范围，返回逐行结果，避免部分成功不可见。
5. 统一跨模块错误类别，便于前端处理和运维排查。
6. 成绩发布固化规则版本和输入值，支持审计与受控重算。
7. 课程管理边界和对外查询能力单独成节，减少组员之间的职责重叠。

## 仍需团队或业务方确认的内容

两版都不能代替业务决策。以下参数在上线前必须得到书面确认：

- 总评权重、精度、及格线和 GPA 换算；
- 补考、缓考、重修对最终成绩与 GPA 的影响；
- 部分课时请假的考勤状态认定规则；
- 累计请假或缺勤达到课程课时比例时的统计口径和处理结果；
- 辅导员是否可修改课程基础信息；
- 哪些岗位属于“课程管理员”和“教务审批人员”；
- 学委课表变更申请需要哪些审批节点。

## 推荐采用方式

以 V2 第 8 节 C01 至 C08 为评审清单，由涉及模块负责人和业务负责人逐项确认。确认后把文档状态改为“已批准”，记录批准人和日期，并把权限结论同步回 PRD、权限初始化脚本与接口文档。任何影响其他模块的数据结构或语义变更，都先修改规范并完成评审，再合并代码。
