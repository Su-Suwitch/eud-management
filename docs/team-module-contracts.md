# 学院管理系统模块协作规范

版本：V0.1
日期：2026-10-11
状态：建议稿，待团队负责人和相关模块负责人确认

本规范依据《学院管理系统需求文档》PRD V1.0，解决班级数据归属、成绩管理、请假与考勤联动、角色权限冲突四项问题。目标是让每位组员可以独立开发模块，同时避免重复建表、互相覆盖数据和联调时临时修改业务规则。

本文提出的接口名称和字段是团队契约建议，尚未代表仓库中已有实现；表名与现有团队数据库设计对齐后再落地。确认本规范后，应同步更新需求中的权限矩阵及接口文档。未确认的争议项不得按各自理解分别实现。

## 一 通用协作规则

1. 每类核心数据只有一个负责模块。其他模块通过公开 Service/API 查询或请求变更，不直接调用对方 Mapper 写入数据。
2. 同一后端进程优先采用公开 Java Service/API，不为模块协作额外引入微服务或消息队列。下文接口是业务契约，不要求全部暴露为 HTTP 接口。
3. 跨模块传递稳定 ID，姓名、班级名称、课程名称仅用于展示，不作为关联键。业务档案 ID 与登录用户 ID 必须区分，不能直接互换。
4. 教学业务记录包含学期归属；所有查询和变更遵循框架的租户隔离、逻辑删除和数据权限。归档学期禁止修改业务记录。
5. 权限必须在后端校验。隐藏按钮只负责界面体验，不能替代接口授权；列表、详情、导出、批量接口执行相同的数据范围限制。
6. 每个负责人交付表结构或迁移脚本、接口说明、页面和权限配置，以及相关业务校验。联调前提供最小示例数据。

## 二 班级和学生关系

### 数据归属

| 数据 | 负责模块 | 其他模块的使用方式 |
| --- | --- | --- |
| 年级、班级、班级所属年级及专业 | 年级管理 | 查询并引用 gradeId、classId |
| 学生档案、学生当前班级、调班历史 | 学生管理 | 按学生 ID 或班级 ID 查询 |
| 辅导员档案、辅导员所带班级分配 | 导员管理 | 查询班级的主辅导员及其所带班级 |
| 课程、按学期开课、开课教师和行政班关联 | 课程管理 | 课表、考勤、学习和考务引用 courseId、offeringId |

一个班级只有一条基础记录，不允许课程、考勤、宿舍等模块另建“业务班级主表”。课程的教学班或开课实例可以关联多个行政班，不能与行政班混为同一实体。

班级上的主辅导员关系建议由导员模块负责变更；年级模块的编辑页面调用其公开接口。关系只存一份，可采用班级的 counselorId 字段，也可采用唯一的关系表，二者不同时维护。班主任分配由年级模块负责，并校验教师档案存在。

### 公共查询契约

- `ClassApi.getClass(classId)`：返回班级 ID、编码、名称、年级、专业、院系、状态。
- `ClassApi.listClasses(query)`：支持按年级、专业、院系查询，返回调用者有权查看的班级。
- `StudentApi.listStudentsByClass(classId)`：返回有权访问的学生 ID、姓名、学号和当前状态。
- `CounselorApi.getPrimaryCounselor(classId)`：查询该班级当前主辅导员。
- `CounselorApi.assignPrimaryCounselor(classId, counselorId)`：校验并变更主辅导员，记录操作人和变更时间。

用户身份从认证上下文获取，不允许前端提交 actorUserId 来冒充操作人。后台任务调用时使用明确的系统执行身份。

### 变更规则

班级删除前检查学生和有效业务引用。有引用时禁止删除，采用停用；历史课表、考勤、成绩仍可追溯。学生调班由学生模块完成并记录生效时间，不能直接把旧考勤、成绩等历史记录重新归入新班级。

需要按历史班级统计的业务记录，应保存发生时的班级关系或使用带有效期的关系查询。仅用于当前学生列表的查询，使用学生当前班级。

## 三 成绩存储和计算

### 职责划分

**学习管理负责课程成绩和统一计算规则；考务管理负责考试场次及其原始成绩。** 两者保存不同层级的事实，不维护两份可独立修改的课程总评。

| 数据或操作 | 负责模块 | 边界 |
| --- | --- | --- |
| 考试场次、参考学生、签到、考试原始分 | 考务管理 | 可按场次录入和更正原始分 |
| 平时分、实验分、课程考试分、总评 | 学习管理 | 统一管理课程成绩及其发布状态 |
| 总评权重、成绩取值规则、GPA 和学分 | 学习管理 | 统一配置、校验、计算和留存版本 |
| 考试分数分布和场次及格率 | 考务管理 | 根据该考试场次原始分统计 |
| 学期挂科数、GPA、已修学分 | 学习管理 | 根据已发布课程成绩统计 |

课程总评按“学生修读记录”唯一；修读记录关联开课实例，开课实例关联课程和学期。每个考试场次中，同一学生只保留一份当前原始成绩，同时留存更正记录。

### 成绩同步契约

考务模块通过 `GradeApi.syncExamScores(command)` 提交考试原始分。命令至少包含 examId、offeringId、学生修读 ID、score、sourceRevision。学习模块返回每条记录的成功或失败原因。

学习模块必须校验考试与开课对应关系、学生修读资格、分数范围、学期归档状态和成绩锁定状态。幂等键采用“考试场次 + 修读记录 + 来源版本”；同版本重复请求不得重复处理，旧版本不得覆盖新版本。

来源版本由考务模块每次更正时递增，不能由前端任意指定。学习模块保留考试来源和版本，便于追溯。

同一课程存在期中、期末、补考等多个考试时，必须明确每个考试的成绩用途和计算规则。未配置映射关系时，原始分只保存到考务模块，不能以“最后录入的考试分”覆盖课程考试分。

### 统一计算规则

1. 总评采用配置后的分项加权，权重合计必须为 100%。例如平时 30%、实验 20%、考试 50%；该比例只是示例，不是系统固定默认值。
2. 分数范围、及格线、四舍五入精度、GPA 换算和重修/补考处理方式由学习模块集中配置。后端使用十进制定点计算，前端只展示结果。
3. 未录入与 0 分区分。必需分项缺失时，成绩保持未完整状态，不能自动按 0 分发布。
4. 成绩建议采用“草稿 → 已提交 → 已发布 → 已锁定”状态。GPA、挂科预警和获得学分以已发布及已锁定成绩为准，草稿不得进入正式统计。
5. 发布时保存计算规则版本与结果；修改规则不能静默重算历史已发布成绩。需要重算时由授权人员发起，记录影响范围并重新发布。
6. 教师录入课程成绩的权限由学习管理提供；考务录入权限单独配置，不因教师可以录入课程成绩就自动允许其修改任何考试场次。

## 四 请假与考勤联动

### 数据归属

请假模块负责申请、证明材料、审批链和最终结果；考勤模块负责课程签到事实、考勤记录及最终考勤状态。

请假模块不直接更新考勤表。只有最后一级审批通过，才调用 `AttendanceApi.applyApprovedLeave(command)`。命令包含 leaveId、studentId、startTime、endTime、approvalRevision；考勤模块核验最终审批事实及版本，不能仅相信前端传来的“已通过”。

### 请假覆盖和状态计算

第一版建议采用明确规则：请假区间完整覆盖一节课的实际起止时间，该节课可计为“请假”；只覆盖部分时间的记录标为待处理，由授权人员确认。时间区间统一采用左闭右开，并统一时区。

请假申请保存起止时间；按节判断由考勤模块使用实际课时完成，不能根据请假天数直接整日覆盖。

原始打卡事实保留，不因请假而删除或改写打卡时间、位置、方式。已经签到的记录保留实际到课状态，同时保留请假关联；没有签到且被有效请假完整覆盖的记录显示“请假”。规则计算产生的迟到、缺勤等状态与人工修正记录分开保存，请假联动不能静默覆盖人工修正；有冲突时列入待处理。

考勤生成未来记录或重新计算时，也必须查询有效请假覆盖范围。审批通过时没有考勤记录，不代表请假同步失败，不能只处理当时已存在的记录。

### 一致性和重试

1. 幂等键为 leaveId + approvalRevision。同一审批结果重试不能生成重复覆盖关系。
2. 同一数据库且可使用同一事务时，最终审批落库与考勤联动一起提交。
3. 无法共用事务时，审批结果与待同步任务一起落库；任务记录同步状态、次数和错误，失败后重试。审批已通过但联动未完成时，界面明确显示“考勤同步中/失败”，不能显示同步已完成。
4. 再次处理时查询当前申请状态和版本，避免过期的“通过”任务在申请取消后重新生效。
5. 审批前撤回不触发考勤变更。审批通过后的取消走独立授权流程，完成后调用 `AttendanceApi.revokeApprovedLeave(leaveId, revision)`。
6. 取消时移除该申请的覆盖关系，根据原始签到事实、其他有效请假和人工修正重新计算；不能把所有记录简单改成“缺勤”。
7. 审计记录包含申请、审批版本、受影响课时、变更前后状态、操作身份和时间。归档学期的更正须走单独授权流程。

### 首版验收场景

- 多级审批中间环节通过，考勤不变化；最后一级通过才生效。
- 重复同步同一审批结果，结果不重复。
- 审批时未来考勤尚未生成，后续生成仍正确识别请假。
- 学生请假但实际到课，保留签到事实和请假关联。
- 一次请假取消后，另一份有效请假仍能覆盖对应课时。
- 同步失败可重试，过期版本不覆盖新状态。

## 五 权限冲突处理建议

统一将权限分为查看、申请、维护、审核四类，分别授权；“只读”不代表不能拥有特定申请动作，“读写”也不代表拥有全部审核权。

| 争议项 | 建议最终规则 | 数据范围和限制 |
| --- | --- | --- |
| 学委的课程表权限 | 查看本班课表；首版不开放直接排课、调课、删除 | PRD 职责表写读写，权限矩阵写只读；建议按只读落地，协助反馈通过申请或通知处理 |
| 教师的补卡审核 | 增加独立补卡审核权限，不授予全面修改考勤规则的权限 | 仅本人授课课时的学生；不得审核本人提交的申请 |
| 纪委的补卡审核 | 可审核本班学生补卡，不跨班 | 不得审核本人申请；本人申请交由授课教师或辅导员处理 |
| 教师的调停课权限 | 查看课表、提交本人授课任务的调停课申请 | 提交申请不直接修改课表；教务授权人员审核通过后才生效 |
| 排课与调课审批 | 管理员及获明确授权的教务人员处理 | 管理员负责排课；辅导员是否有排课维护权需团队确认，不从笼统“读写”自动推导 |

建议权限标识分别采用 `edu:schedule:query`、`edu:schedule:change-apply`、`edu:schedule:change-approve`、`edu:attendance:makeup-apply`、`edu:attendance:makeup-approve`。不要为了一个审核操作授予整个模块的 update 权限。

补卡申请在教师和纪委均有审核资格时，第一名合法审核者完成后即结束，使用状态条件更新或版本锁防止重复审批；不采用双方先后审批，除非团队另外要求。

所有审核要求申请仍处于待审状态，操作人属于合法审核范围；审核意见与结果留痕。用户兼有多个角色时，可合并动作权限，但每次操作的数据范围按该动作对应的合法关系判断，不能因为同时拥有学生与教师角色就扩大到全校。

### 本模块课程管理权限

课程管理按 PRD 权限矩阵处理：管理员和辅导员具有维护权限，教师、学生、学委、纪委具有查看权限。涉及开课班级分配时，辅导员仅能维护本人负责班级的关系；教师查看本人授课信息，学生查看与本人修读相关的信息。

课程库属于共享数据，辅导员可以修改哪些院系的课程基础信息，PRD 未明确。建议由管理员按院系配置课程维护范围；未配置范围时，不允许辅导员修改全校共享课程。课程基本信息中的公开字段可以单独开放只读查询，教师联系方式等个人信息不随课程查询自动公开。

## 六 开工前确认清单

| 确认项 | 参与负责人 | 推荐结论 |
| --- | --- | --- |
| 班级、学生班级归属和辅导员分配的数据归属 | 年级、学生、导员 | 按第二节执行，关系只存一份 |
| 课程开课实例及教师、班级关联归属 | 课程、课表、学习、考务 | 课程模块提供稳定 offeringId，其他模块引用 |
| 成绩主数据和各考试用途 | 学习、考务 | 学习维护课程总评，考务维护场次原始分 |
| 权重、及格线、精度、GPA 和补考规则 | 学习、考务、团队负责人 | 集中配置并版本化；先确认第一套规则 |
| 请假部分覆盖课时的处理 | 请假、考勤、团队负责人 | 首版完整覆盖自动生效，部分覆盖待处理 |
| 学委课表、补卡审核和教师调课权限 | 课表、考勤、权限负责人 | 按第五节建议收敛并修改 PRD 权限矩阵 |
| 课程共享数据维护范围和辅导员排课权限 | 课程、课表、权限负责人 | 维护范围显式授权，不默认全校可写 |
| 联调接口、状态和错误码 | 所有相关模块 | 在接口文档固定后再独立实现 |

确认方式：由团队负责人在组内确认版本，各模块负责人认领对应的数据和接口；确认后的修改需要通知受影响负责人并更新版本。未实现的跨模块接口可以先提供模拟数据，但字段、ID 类型和业务规则必须与约定一致。
