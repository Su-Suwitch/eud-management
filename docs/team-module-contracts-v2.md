# 学院管理系统跨模块协作规范 V2

版本：V0.2
日期：2026-10-11
状态：商用基线评审稿
适用范围：班级、课程、学习、考务、请假、考勤、课表模块

## 1 目的

本规范解决四个会影响多人并行开发的问题：班级数据由谁维护、成绩由谁保存和计算、请假审批如何影响考勤、需求文档中的权限矛盾如何落地。

本项目基于 Yudao 单体应用开发。同步业务校验优先使用 Java Service；需要可靠重试的跨模块状态传播采用“业务事务 + 本地消息表（Transactional Outbox）+ 定时重试”，不强制引入外部消息队列。本文中的接口名是职责示例，负责人可以按照仓库命名习惯调整，但数据归属、输入输出、幂等规则和业务结果不得自行改变。

## 2 全组统一规则

### 2.1 一份数据只有一个写入方

每类核心数据指定一个负责模块。负责模块拥有建表、增删改、校验和审计责任；其他模块可以读取或调用负责模块的 Service 请求变更，不得直接调用其 Mapper、复制同类主表或绕过校验写数据库。

### 2.2 统一使用稳定 ID

模块间使用 `Long` 类型业务主键关联。姓名、学号、班级名称、课程名称仅用于展示和搜索，不作为关联键。必须区分：

- `userId`：Yudao 系统登录用户 ID；
- `studentId`、`teacherId`、`counselorId`：学院业务档案 ID；
- `classId`：行政班 ID；
- `courseId`：课程目录 ID；
- `offeringId`：某课程在某学期的一次开课 ID；
- `enrollmentId`：某学生参加某次开课的修读关系 ID。

考勤、成绩、考试和课表应优先关联 `offeringId`，不能只关联 `courseId`。同一门课程在不同学期、教师和班级下的数据必须能够区分。

### 2.3 权限由动作和数据范围共同决定

后端同时校验“能做什么”和“能操作哪些数据”。前端隐藏按钮不等于授权。查询、详情、导出、批量操作也必须执行数据范围校验。

权限动作统一拆分为：

- `query`：查看；
- `create`、`update`、`delete`：维护业务数据；
- `apply`：发起申请；
- `approve`：审核申请；
- `export`：导出。

禁止用一个笼统的 `update` 权限同时代表直接修改、发起申请和审核。

### 2.4 删除和历史数据

已经被业务记录引用的数据原则上停用，不物理删除。学生转班、教师变更、课程停用不得改变过去学期的考勤、成绩和课表归属。所有业务表遵守 Yudao 的租户、逻辑删除、创建人和更新时间约定。

### 2.5 商用一致性和审计基线

1. 所有创建、更新、审批、发布、撤销和导出接口必须具备后端权限校验、参数校验和数据范围校验。
2. 审批、成绩发布、规则切换等关键记录增加版本号，更新时使用乐观锁或状态条件更新，防止并发覆盖。
3. 跨模块命令必须定义幂等键。相同请求重复提交不得产生重复记录或重复状态变更。
4. 关键业务操作保存操作人、操作时间、原因、变更前值和变更后值。审计日志不得记录身份证号、手机号、附件地址等完整敏感信息。
5. 批量导入先校验再提交；采用全部成功或明确的分批事务，返回逐行结果。不得出现界面显示失败但部分数据已静默写入。
6. 导出属于独立权限，记录导出人、条件、数量和时间。敏感字段按角色脱敏，禁止仅依赖前端隐藏列。
7. 对外接口统一错误码，至少区分数据不存在、状态不允许、无数据权限、重复数据、并发冲突和下游同步失败。

## 3 班级数据规范

### 3.1 最终决定

年级管理模块是年级和行政班主数据的唯一维护方。其他模块只能引用 `gradeId` 和 `classId`，不得建立自己的班级主表。

| 数据 | 唯一写入模块 | 说明 |
| --- | --- | --- |
| 年级基础信息 | 年级管理 | 年级名称、入学年份、院系、专业 |
| 行政班基础信息 | 年级管理 | 班级编码、名称、所属年级和专业、状态 |
| 学生档案及当前班级 | 学生管理 | 学生档案保存 `classId`，调班由学生模块办理 |
| 班级主辅导员分配 | 导员管理 | 关联现有 `classId`，一个班级仅一个当前主辅导员 |
| 班主任分配 | 年级管理 | 关联现有 `teacherId` |
| 开课与行政班关系 | 课程管理 | 关联 `offeringId` 与一个或多个 `classId` |

这里的“课程班级关系”不是新的班级。它只表示哪些行政班参加一次开课。

### 3.2 对外能力

年级管理至少提供以下只读能力：

```text
getClass(classId)
getClassList(deptId, gradeId, majorId, status)
validateClassIds(classIds)
```

学生管理至少提供：

```text
getStudent(studentId)
getStudentsByClass(classId, status)
```

导员管理至少提供：

```text
getPrimaryCounselor(classId)
getManagedClassIds(counselorId)
```

调用方只依赖返回对象，不依赖对方数据库表结构。Service 返回不存在、已停用或无权访问时，调用方必须终止当前写操作。

### 3.3 业务规则

1. 班级编码在同一租户内唯一。
2. 班级存在学生、开课或历史记录时不可删除，只能停用。
3. 学生调班由学生模块完成，记录原班级、新班级、生效日期、原因和操作人。
4. 历史报表按业务发生时保存的 `classId` 统计，不跟随学生当前班级变化。
5. 课程、考勤、学习、考务、宿舍模块的班级下拉框统一读取年级管理提供的数据。

## 4 成绩数据规范

### 4.1 最终决定

考务管理负责考试场次和考试原始分；学习管理负责课程总评、学分、GPA 和学业预警。两个模块保存的对象不同，不允许各自维护一份课程总评。

| 数据 | 唯一写入模块 | 用途 |
| --- | --- | --- |
| 考试场次、时间、地点 | 考务管理 | 组织考试 |
| 某学生某场考试的原始分 | 考务管理 | 场次统计、提供课程考试分来源 |
| 平时分、实验分、考试分、总评 | 学习管理 | 形成课程最终成绩 |
| 课程成绩计算规则 | 学习管理 | 权重、及格线、精度 |
| GPA 规则和已修学分 | 学习管理 | GPA、学分和学业预警 |

课程成绩以 `enrollmentId` 为唯一对象。考试原始分以 `examId + enrollmentId` 唯一。

### 4.2 同步方式

在同一个 Yudao 后端中，考务模块录入或更正考试成绩后，调用学习模块公开 Service：

```text
syncExamScore(examId, offeringId, enrollmentId, score, sourceRevision)
```

学习模块完成以下校验：

1. 考试场次属于该 `offeringId`；
2. 学生确实存在对应 `enrollmentId`；
3. 分数在 0 至 100 之间；
4. 学期未归档，课程成绩未锁定；
5. 该考试已被配置为期中、期末、补考等明确用途；
6. `sourceRevision` 大于学习模块已处理的来源版本。

单条录入时，考务原始分和学习模块成绩分项在同一数据库事务中提交；任何校验失败则整体回滚。批量导入使用同一校验逻辑，按明确批次事务提交并逐行返回结果。学习模块以 `examId + enrollmentId + sourceRevision` 保证幂等，旧版本不得覆盖新版本。

如果后续将考务和学习拆分为独立服务，必须改用事务消息或 Outbox 可靠投递，不能保留跨库事务假设。

### 4.3 计算规则

1. 总评公式配置在学习模块，例如“平时分 30% + 实验分 20% + 期末考试 50%”。具体权重由团队或教务确认，系统不擅自固定。
2. 权重之和必须为 100%。无实验课程可以不启用实验分项。
3. “未录入”使用空值表示，与 0 分严格区分。必填分项未录入时不能发布总评。
4. 后端使用十进制定点计算，并统一四舍五入位数；前端不得自行重新计算。
5. 成绩状态采用“草稿、已提交、已发布、已锁定”。教师可编辑草稿；提交后等待授权人员复核；发布后进入学生查询、统计和预警；锁定后只能通过带原因和审计记录的更正流程修改。
6. GPA 和获得学分只根据已发布或已锁定的课程总评计算。
7. 补考和重修不能直接覆盖历史原始成绩。系统必须保留原成绩、补考或重修成绩、最终采用成绩及采用规则。
8. 已发布成绩修改时必须记录修改前值、修改后值、原因和操作人。
9. 成绩发布时保存计算规则版本、各分项原值和最终结果。修改计算规则不得静默重算历史已发布成绩；需要重算时创建批次任务，记录范围、规则版本、执行人和结果。

### 4.4 必须由团队确认的成绩参数

- 总评各分项权重；
- 总评保留的小数位；
- 及格线；
- GPA 换算表；
- 补考成绩是否封顶以及如何计入 GPA；
- 重修后是否替换原学分和 GPA。

参数未确认前可以完成表结构和流程，但不能把示例值写死为正式规则。

## 5 请假与考勤联动规范

### 5.1 最终决定

请假模块负责申请、材料、审批过程和最终审批结果；考勤模块负责打卡事实和考勤状态。请假模块不得直接修改考勤表。

只有请假完成全部审批并成为“已通过”状态后，请假模块才调用：

```text
applyApprovedLeave(leaveId, approvalRevision, studentId, startTime, endTime)
```

撤销已通过请假时调用：

```text
revokeApprovedLeave(leaveId, approvalRevision)
```

两个接口都必须幂等，幂等键为 `leaveId + approvalRevision + action`。处理前重新读取请假的当前状态和版本，旧版本事件不得覆盖新状态。

### 5.2 状态处理

考勤模块保留学生原始打卡记录，包括时间、位置、方式和设备信息。请假只影响“最终考勤状态”，不得删除或伪造原始打卡事实。

采用以下判定：

| 场景 | 最终处理 |
| --- | --- |
| 已批准请假完整覆盖某节课，学生未打卡 | 状态为请假 |
| 已批准请假完整覆盖某节课，学生已正常打卡 | 保留正常到课，同时记录该课时存在请假 |
| 请假只覆盖某节课的一部分 | 标记待人工确认，不自动改为请假 |
| 请假审批未完成或被驳回 | 不影响考勤 |
| 请假被撤销 | 移除该请假影响，依据原始打卡重新计算 |

时间统一使用系统约定时区。是否覆盖一节课，由考勤模块根据实际上课起止时间判断，不按“请了几天”粗略处理。

这里的“部分课时认定规则”仅指一张请假单没有完整覆盖某节课时，该节考勤应认定为请假、迟到、早退或人工确认。它与“累计请假或缺勤超过课程课时的某个比例，是否取消考试资格或判定不合格”是两项独立规则。

累计课时比例属于课程考核资格规则，由课程、考勤和学习模块共同使用，不能直接写死为“超过 1/3 挂科”。上线前必须由业务方确认：分母采用计划课时还是实际课时、批准请假是否计入、迟到早退如何折算、阈值是达到还是超过，以及触发结果是预警、取消考试资格还是课程不合格。规则应配置化并保存版本，计算结果保留明细依据；规则变化不得追溯覆盖已经确认的历史结果。

### 5.3 已有和未来考勤记录

审批通过时，考勤模块处理时间范围内已经存在的考勤记录。之后新生成课次或执行考勤统计时，仍需查询该学生有效的已批准请假，保证未来课次也能识别。

建议考勤模块保存 `leaveId` 关联，用于撤销和审计；不得只把状态改成“请假”而丢失来源。

### 5.4 异常和审计

1. 最终审批结果与一条待处理 Outbox 事件在同一数据库事务中落库。审批成功不依赖考勤投影当场完成，也不会因为进程中断丢失联动任务。
2. 后台任务投递 Outbox 事件，考勤模块按幂等键处理并回写同步状态。失败记录错误、次数和下次重试时间；达到阈值后告警并进入人工处理队列。
3. 请假详情展示考勤同步状态：待同步、同步中、已完成、部分失败、失败。不得把“审批通过”展示成“所有考勤已更新”。
4. 人工修改过的考勤记录不被请假同步静默覆盖，出现冲突时进入待处理列表。
5. 审计信息至少包含 `leaveId`、审批版本、学生、受影响课次、变更前状态、变更后状态、操作时间和操作人。
6. 取消已批准请假时产生新的撤销事件。考勤模块移除该请假影响后，根据原始打卡、其他有效请假和人工修正重新计算，不能直接改成缺勤。

## 6 权限冲突的统一结论

需求文档中的职责描述和权限矩阵存在不一致。开发时先采用以下最小权限方案，并由负责人确认后同步回需求文档。

| 角色和争议 | 统一实现建议 | 数据范围 |
| --- | --- | --- |
| 学委课表变更 | 可以查看本班课表，为本班发起并编辑调课、补课申请；申请生效前不能直接改正式课表 | 本班级，不得跨班 |
| 教师课表变更 | 可以查看本人课表，为本人授课任务发起并编辑调课、停课、补课申请；申请生效前不能直接改正式课表 | 本人授课开课实例 |
| 调停课审批 | 管理员或明确配置的教务人员审批 | 授权院系或全校 |
| 学生补卡 | 可以提交本人补卡申请 | 本人考勤记录 |
| 教师补卡审核 | 可以审核本人授课课次的补卡 | 本人授课学生 |
| 纪委补卡审核 | 可以审核本班同学的补卡 | 本班级，不含本人申请 |
| 辅导员考勤 | 可以维护和审核本人负责班级的考勤 | 所带班级 |

当教师和纪委都具备审核资格时，任一合法审核人完成审核即结束流程，不要求重复审核。审核更新必须包含“当前状态为待审核”和版本号条件；受影响行数为 0 时返回并发冲突，避免两人同时提交造成重复处理。

建议权限标识：

```text
edu:schedule:query
edu:schedule:change-apply
edu:schedule:change-approve
edu:attendance:query
edu:attendance:makeup-apply
edu:attendance:makeup-approve
```

审核人不能审核自己的申请。用户拥有多个角色时，每个动作仍按对应业务关系计算数据范围，不能把多个局部权限合并成全校权限。

教师和学委对课表的“更改”统一落为课表变更单：草稿阶段可编辑、删除和撤回；提交后进入冲突检测与审批；审批通过后由课表模块一次性更新正式课表并通知受影响人员。教师或学委不能直接更新正式排课记录，也不能审批自己提交的变更。这样既满足其调课、补课操作需要，也保留正式课表的审计链和冲突校验。

## 7 课程管理模块的边界

课程管理负责：

- 课程目录和课程分类；
- 每学期的开课实例；
- 开课与授课教师关系；
- 开课与行政班关系；
- 课程大纲附件；
- 课程数据导出。

课程管理不负责：排课时间和教室、调停课审批、学生成绩、考试安排、课堂考勤。

### 7.1 精简表结构

课程管理采用三张核心业务表：

| 表名 | 职责 |
| --- | --- |
| `edu_course` | 课程基础信息、院系、专业、课程类型、学分、学时和课程大纲附件 |
| `edu_course_offering` | 一门课程在一个学期的一次开课，关联 `courseId` 和 `termId` |
| `edu_course_offering_relation` | 统一保存开课与教师、行政班的多对多关系 |

`edu_course_offering_relation` 使用 `target_type` 区分教师和行政班，使用 `target_id` 保存对应业务 ID；教师关系可通过 `target_role` 区分主讲和助教。表上建立 `tenant_id + offering_id + target_type + target_id` 唯一约束，并为 `target_type + target_id` 建立查询索引。所有写入必须由课程 Service 按目标类型调用教师或班级接口校验，其他模块不得直接写该关系表。

课程分类暂不单独建表。课程通过 `dept_id`、`major_id` 和 `course_type` 分类：院系复用 `system_dept`，专业引用年级模块的专业 ID，课程类型使用数据字典；前端可按“院系 → 专业 → 课程类型”生成分类树。

课程大纲文件本体复用 `infra_file`，`edu_course` 保存文件 ID 集合，不新增课程附件表。当前需求未明确个人选课、退选、免修等流程，因此暂不创建学生修读关系表；成绩、考勤和考务先使用 `offering_id + student_id` 标识学生在一次开课中的业务记录。后续确认个人选课或重修流程时，再增加可审计的修读关系，不能把该流程塞进开课关系表。

`edu_course` 与 `edu_course_offering` 必须分开：课程是跨学期复用的目录数据，开课是带学期、教师和班级的业务实例。成绩、考勤和考试记录也必须使用各自业务表，不合并进课程表。

课程基础信息是共享主数据，只有管理员或课程管理员可以增删改。辅导员可以查看课程，并维护本人所带班级与开课实例的关联；教师和学生按本人关系查看。若业务方确实要求辅导员修改课程基础信息，必须显式配置院系范围和独立权限，不授予全校写权限。

课程模块至少向课表、学习、考务和考勤模块提供：

```text
getCourse(courseId)
getOffering(offeringId)
getOfferingTeachers(offeringId)
getOfferingClassIds(offeringId)
validateStudentOffering(studentId, offeringId)
```

## 9 联调和验收要求

每个模块负责人在联调前提供：接口方法或接口文档、请求与返回示例、权限标识、错误码、最小测试数据。跨模块联调至少覆盖以下场景：

1. 班级停用后，不能新建关联，但历史课程和成绩仍可查询。
2. 学生调班后，旧学期成绩和考勤仍归原班级统计。
3. 考试分数同步失败时，考务和学习模块不出现一边成功、一边失败。
4. 成绩缺少必填分项时无法发布，0 分可以正常保存。
5. 请假只有最终审批通过才影响考勤，重复同步不重复修改。
6. 请假撤销后依据原始打卡重新计算，不直接改成缺勤。
7. 教师和学委可以创建并编辑权限范围内的课表变更单，但不能直接修改正式课表，也不能审批本人申请。
8. 部分课时请假与累计课时比例分别计算，比例规则可以追溯到课时明细和规则版本。

本规范经团队确认后作为跨模块开发基线。后续修改影响其他模块时，应先更新本文并通知相关负责人，再修改代码。
